# «Созвездие»: распределение работы на 5 человек

> Рабочий документ команды. Это не пересказ PDF, а ответ на вопрос «кто что делает, чтобы работа одного не блокировала остальных».
>
> **Источники:** `Созвездие.pdf` (18 страниц), `Созвездие план действий.md`.
> **Уровень:** базовый. **Срок:** подготовка + 6 занятий по 1 часу + онлайн-доработка.
> **Стек:** Kotlin, Jetpack Compose, Firebase Authentication / Realtime Database / Storage, Room, Android Studio, GitHub.

Документ рассчитан на 5 исполнителей.

- Если **наставник — шестой**, он не входит в эти 5: его роль — ревью, помощь с Firebase и сборкой, разбор блокеров. Роль Р1 тогда берёт самый сильный из школьников.
- Если **наставник входит в 5**, он берёт Р1, а четверо школьников — Р2–Р5. Если школьников пять, Р1 — школьник-тимлид, наставник только ревьюит.
- PDF изначально предполагает схему «наставник + один школьник». Пять человек — расширение; на защите нужно объяснить роли, за «организацию» дают 5 баллов.

## 0. Сводка на один экран

| # | Роль | Что делает | Папки | Результат |
|---|---|---|---|---|
| **Р1** | Архитектор и интегратор | Каркас, контракты, Firebase-консоль, сборка, релиз, ревью | `core/`, `navigation/`, gradle, manifest | Шаблон, который собирается; APK; зелёный `main` |
| **Р2** | Авторизация и профиль | Регистрация, вход, выход, сессия, профиль | `feature/auth/`, `feature/profile/`, `data/auth/` | Сценарий auth из PDF работает на устройстве |
| **Р3** | Интерфейс чатов | Список чатов, диалог, тема, UI-компоненты | `feature/chats/`, `core/ui/` | Два экрана + единый визуальный стиль |
| **Р4** | Данные и синхронизация | Realtime Database, Room, сообщения, статусы, офлайн | `data/chat/`, `data/message/`, `data/local/` | Сообщения в реальном времени + история |
| **Р5** | Медиа, качество, документация | Картинки, тест-план, README, видео, презентация | `feature/media/`, `data/media/`, `docs/`, `presentation/` | Отправка изображений + пакет сдачи |

**Три правила, на которых держится параллельность:**

1. **Контракт раньше кода.** В неделю 0 Р1 фиксирует модели, интерфейсы репозиториев, маршруты и имена классов. Сигнатуры меняются только через PR в `core/contracts/` и сообщение в чат.
2. **Одна папка — один хозяин.** Никто не редактирует чужие файлы. Нужно изменение — issue с тегом владельца, не правка руками.
3. **Заглушка вместо ожидания.** Каждая реализация начинается как stub с тестовыми данными. Владелец заменяет внутренности на Firebase, **не меняя сигнатуры**. Поэтому Р3 может рисовать чат, пока Р4 не подключил базу, а Р2 может сделать вход, пока чатов ещё нет.

- MVP мессенджера для **Android 6.0 (API 23) и выше**, язык **Kotlin**, среда **Android Studio**, сборка в **APK**.
- 6 занятий по 1 часу, роли в кейсе: наставник (тимлид) + школьник (разработчик). Онлайн-поддержка между занятиями.

### 1.2. Базовый уровень: что входит и что не входит

Входит: email + пароль через Firebase Authentication, текстовые сообщения в реальном времени, профиль, история, упрощённая отметка «прочитано», изображения, Jetpack Compose.

Не входит (это продвинутый уровень, не берём): голосовые сообщения, «печатает…», «в сети», поиск по чатам, групповые чаты, «доработанный современный UI» как отдельная цель.

### 1.3. Что сдаём

1. Рабочее приложение + **APK**.
2. **Репозиторий GitHub** с исходниками и **README**.
3. **Видео** демонстрации (резерв на защите).
4. **Презентацию** из 7 разделов и защиту 7 минут.

## 2. Принцип разбиения

Пять зон — это не «UI-команда, которая ждёт бэкенд», а зоны с законченным результатом и жёсткими границами файлов. Где результат требует двух зон (чат = интерфейс + данные), они договариваются контрактом, а не правят общий файл:

```
                    ┌─────────────────────────────┐
                    │  Р1: каркас + контракты     │
                    └──────────────┬──────────────┘
          ┌────────────────┬───────┴────────┬────────────────┐
          ▼                ▼                ▼                ▼
      Р2: auth        Р3: UI чатов     Р4: данные       Р5: медиа
          │                │                │                │
          └────────────────┴───────┬────────┴────────────────┘
                                   ▼
                    интеграция, сборка, релиз (Р1)
```

Почему не мешают друг другу:

- **Р3 не ждёт Р4:** интерфейс получает `List<Chat>` и `List<Message>` из интерфейсов; пока данных нет — stub возвращает тестовые.
- **Р2 не ждёт Р4:** регистрация и вход не зависят от чатов; профиль пишет только узел `users/{uid}`.
- **Р5 не ждёт готовности всего:** тест-план, README и шаблон презентации пишутся с первого дня; медиа подключается к готовому контракту `MediaRepository`.
- **Р1 не пишет фичи:** он владеет только инфраструктурой и сборкой. Это снимает главный конфликт «все правят `build.gradle`».

PDF прямо рекомендует наставнику разделить команду на UI, Firebase, локальное хранение и презентацию. Наша схема это и делает, добавляя авторизацию (её в рекомендации нет, а 10 баллов за неё есть) и отдельного интегратора, который держит сборку.

## 4. Роли подробно

### Р1 — Архитектор и интегратор

**Зона:** фундамент проекта, контракты, Firebase-консоль, сборка, ревью, релиз.
**Не трогает:** экраны и бизнес-логику фич (только ревью и точечные фиксы сборки).

**Неделя 0 (до занятия 1):**
- Создать репозиторий GitHub + проект Android Studio: **Empty Activity (Compose)**, package `com.example.messenger`, **minSdk 23**, Kotlin.
- Зафиксировать зависимости: Compose BOM, Material3, Navigation Compose, lifecycle-viewmodel-compose, Firebase BoM + auth/database/storage, Room + KSP, Coil, `kotlinx-coroutines-play-services`. Версии — из шаблона студии, **не обновлять в процессе**.
- Добавить `INTERNET` в manifest, создать `App.kt`, `MainActivity.kt`, `AppContainer`, `NavHost`, 4 экрана-заглушки.
- Написать `core/contracts/`: модели, интерфейсы, маршруты (код в разделе 5).
- Создать Firebase-проект, подключить Android-приложение, положить `google-services.json` в `app/`, включить Auth (Email/Password), Realtime Database, Storage, вставить rules, включить индексы.
- Создать демо-аккаунты `demo1@example.com` / `demo2@example.com`, завести README-заготовку и `.gitignore`.
- Проверить: `./gradlew assembleDebug` зелёный, APK ставится, приложение открывается.

**Занятия 1–4:** мержить PR, чинить сборку, обновлять контракты по заявкам, следить за `main`, тегировать `v0.1`…`v0.4`, ревьюить код (особенно комментарии — за них 5 баллов).

**Занятие 5:** заморозка фич, сборка release-кандидата, установка на чистый телефон/эмулятор API 23, проверка README «с нуля», тег `v1.0-rc`.

**Занятие 6:** финальный тег, резервная копия APK и видео, проверка слайдов на соответствие PDF.

**Результат:** каркас, в который каждый может вмержить свою папку; зелёный `main`; APK; понятная история PR.
**DoD:** сборка проходит; приложение запускается; контракты не менялись без объявления; README позволяет собрать проект.

### Р2 — Авторизация и профиль

**Зона:** `feature/auth/`, `feature/profile/`, `data/auth/`.
**Не трогает:** `users` читает Р4, но пишет только Р2; чаты и сообщения — не его.

**Неделя 1 (занятие 1):**
- `LoginScreen`, `RegisterScreen` на Compose: email, пароль, подтверждение пароля, кнопка, индикатор загрузки, текст ошибки.
- Валидация: email по шаблону, пароль ≥ 6 символов, поля не пустые.
- `AuthViewModel` + `FirebaseAuthRepository`-**заглушка**: принимает любой пароль, возвращает тестового пользователя. Экраны уже навигируют на чаты.
- Переходы: регистрация ↔ вход, успех → `CHATS` с очисткой back stack.

**Неделя 2 (занятие 2):**
- Реальный `FirebaseAuthRepository`: `createUserWithEmailAndPassword`, `signInWithEmailAndPassword`, `signOut`, `updateProfile(displayName)`, `currentUser`.
- После регистрации — запись `users/{uid}`: email, displayName, createdAt.
- Русские сообщения по `FirebaseAuthException.errorCode`: неверный email, слабый пароль, email занят, неверные данные, нет сети.
- Выход из аккаунта: `signOut()` + `localCache.clear()`; возврат на экран входа.

**Неделя 3 (занятие 3):**
- `ProfileScreen`: email, имя, кнопка «Выйти»; при желании — редактирование имени.
- Проверка сессии: закрыл приложение — открыл, остался внутри. Обработка «пользователь удалён/токен протух».
- Edge cases: пробелы в email, двойной тап по кнопке, поворот экрана, пустой displayName.
- Unit-тест на валидацию email/пароля — это же доказательство «тестов» на защите.

**Недели 4–5:** багфиксы, помощь Р5 с проверкой auth-сценария, финальная полировка текстов ошибок.

**Результат:** полный сценарий PDF «создался → вошёл → вышел → снова вошёл» без крашей.
**DoD:** сессия переживает перезапуск; ошибки понятны на русском; после выхода данные предыдущего пользователя не видны.

### Р4 — Данные и синхронизация

**Зона:** `data/chat/`, `data/message/`, `data/local/`.
**Не трогает:** экраны, auth-экран, Storage-загрузку. Пишет только узлы `chats`, `messages`, `userChats`, `reads`.

**Неделя 1 (занятие 1):**
- Room: `MessageEntity`, `MessageDao`, `MessengerDatabase`, `RoomLocalCache`.
- Заглушки `FirebaseChatRepository`, `FirebaseMessageRepository` на тестовых данных: два чата, 10 сообщений, разные статусы.
- Черновик `docs/rtdb-schema.md`: схема узлов, кто пишет, кто читает.
- Мапперы Entity ↔ доменная модель (без Firebase).

**Неделя 2 (занятие 2):**
- `observeUsers()`: чтение `/users` для экрана «Новый чат».
- `openDirectChat(otherUserId)`: сначала создать `chats/{id}` с `memberIds`, затем двумя записями добавить `userChats` — свой и собеседника. Именно двумя шагами, а не одним multi-path update: rules проверяют `root`, и в одной атомарной записи чат может быть ещё не виден.
- `observeChats()`: слушать `userChats/{uid}`, затем `chats/{chatId}`; собрать `List<Chat>`, посчитать `unread` по `reads`.
- `markRead(chatId)`: записать `chats/{id}/reads/{uid} = ServerValue.TIMESTAMP`.
- `sendText`: push нового сообщения, обновить `lastMessage` / `lastMessageAt` одним `updateChildren`.

**Неделя 3 (занятие 3):**
- `observeMessages(chatId)` = `localCache.observeMessages(chatId)`; Firebase-листенер пишет в Room, UI читает только Room. Это даёт офлайн и единый источник правды.
- Оптимистичная отправка: сначала `SENDING` в Room, потом push, после успеха — `SENT`; при ошибке — `FAILED` + `retry()`.
- `status = READ`, если `reads[другой] >= createdAt`; иначе `SENT`. Считает Р4 в маппере, Р3 только рисует.
- Сортировка по `createdAt`, `limitToLast(200)`, индекс `.indexOn: ["createdAt"]`.
- `createdAt` брать из `ServerValue.TIMESTAMP`, локально — `System.currentTimeMillis()`.

**Неделя 4 (занятие 4):**
- Офлайн: старт из Room, листенер восстанавливается при сети, `info/connected` — по желанию.
- `markRead` при открытии диалога; точка непрочитанного в списке.
- Очистка кэша при смене пользователя (`LocalCache.clear()` вызывает Р2).
- Ретрай `FAILED`, защита от дублей (id сообщения = push key).
- Кэш списка чатов — если успеваем; иначе офлайн демонстрируем внутри открытого диалога.

**Неделя 5:** багфиксы, проверка лимитов, экспорт JSON базы перед защитой (`Data → Export JSON`).

**Результат:** два устройства обмениваются сообщениями за 1–2 секунды; после убийства приложения история на месте; галочка «прочитано» появляется; при потере сети приложение не падает.
**DoD:** unit-тесты на маппер времени/статуса; сценарий «отправил с одного — пришло на второй»; история после перезапуска.

### Р5 — Медиа, качество, документация

**Зона:** `feature/media/`, `data/media/`, `docs/`, `README.md`, `presentation/`.
**Не трогает:** чат-экран (только поставляет `ChatImage` и `ImagePickerButton`), Firebase Auth, RTDB.

**Неделя 0:**
- Шаблон `README.md`: установка, запуск, стек, структура, проверка функций.
- `docs/test-plan.md`: таблица «шаг — ожидание — факт — статус», матрица устройств (API 23 + современный, 5" + 6.7").
- `docs/demo-script.md`: 7-минутный сценарий с таймингом и ролями.
- Папка `presentation/` и каркас 7 слайдов.

**Неделя 1 (занятие 1):**
- `ImagePickerButton(onImagePicked: (Uri) -> Unit)`: `ActivityResultContracts.PickVisualMedia`, без разрешений на старые API (fallback — `GetContent`).
- `ChatImage(url: String)`: Coil, placeholder, ошибка загрузки, скругления, ограничение размера.
- `FirebaseMediaRepository`-**заглушка**: возвращает тестовый URL.

**Неделя 2 (занятие 2):**
- Реальная загрузка: `chat_images/{chatId}/{uuid}.jpg`, `putFile`, `downloadUrl.await()`, прогресс, ошибки.

1. Менять `core/contracts/` может только Р1.

## 6. Схема Firebase

Схему придумывает и поддерживает Р4, rules применяет только Р1. Это разделение важно: один человек не должен иметь возможность случайно сломать доступ всей команде.

### 6.1. Realtime Database

```json
{
  "users": {
    "uid1": { "email": "demo1@example.com", "displayName": "Демо 1", "createdAt": 1730000000000 }
  },
  "userChats": {
    "uid1": { "chatId1": true }
  },
  "chats": {
    "chatId1": {
      "type": "direct",
      "memberIds": { "uid1": true, "uid2": true },
      "lastMessage": "привет",
      "lastMessageAt": 1730000005000,
      "createdAt": 1730000000000,
      "reads": { "uid1": 1730000005000 },
      "messages": {
        "msgId1": {
          "senderId": "uid1",
          "text": "привет",
          "imageUrl": null,
          "createdAt": 1730000005000
        }
      }
    }
  }
}
```

Почему так:

- `userChats/{uid}` — список чатов пользователя. Без него пришлось бы сканировать все чаты: RTDB не умеет фильтровать по вхождению в массив.
- `chats/{id}/reads/{uid}` — время последнего прочтения. Отметка «прочитано» = `reads[другой] >= createdAt` сообщения. Это проще, чем `readBy` на каждом сообщении, и достаточно для базового уровня.
- `memberIds` — объект, а не массив: по нему удобно проверять доступ в rules.
- `messages` — плоский список с `createdAt`; сортировка и `limitToLast(200)`.

Кто пишет:

| Узел | Кто пишет | Кто читает |
|---|---|---|
| `users/{uid}` | Р2 (при регистрации/смене имени) | Р4 (`observeUsers`) |
| `chats/*`, `messages/*`, `reads/*` | Р4 | Р3 через репозитории |
| `userChats/*` | Р4 | Р4 |

### 6.2. Storage

```
chat_images/{chatId}/{messageId}.jpg
```

Путь формирует Р5. Правила — Р1.

### 6.3. Rules для Realtime Database (базовый уровень)

```json
{
  "rules": {
    "users": {
      ".read": "auth != null",
      "$uid": {
        ".write": "auth != null && auth.uid == $uid"
      }
    },
    "chats": {
      "$chatId": {
        ".read": "auth != null && data.child('memberIds').child(auth.uid).exists()",
        ".write": "auth != null && (!data.exists() || data.child('memberIds').child(auth.uid).exists())",
        "messages": {
          ".indexOn": ["createdAt"]
        }
      }
    },
    "userChats": {
      "$uid": {
        ".read": "auth != null && auth.uid == $uid",
        "$chatId": {
          ".write": "auth != null && (auth.uid == $uid || root.child('chats').child($chatId).child('memberIds').child($uid).exists())"
        }
      }
    }
  }
}
```

Что это даёт: читать и писать чат может только участник; чужой `userChats` читать нельзя; создавать новый чат может любой авторизованный (для MVP допустимо).

Список пользователей читается целиком (`users` → `.read: auth != null`) — иначе экран «Новый чат» не сможет показать, кому писать: правила RTDB не дают прочитать родительский узел, если разрешение выдано только на дочерний. Для контура небольшой команды это нормально; для публичного приложения список стоит ограничить доменом почты или отдельным справочником.

Честное ограничение для защиты: участник чата технически может записать сообщение с чужим `senderId` — в rules это не проверяется. Для учебного MVP это приемлемо; в улучшениях указать «ужесточить правила и проверять отправителя».

### 6.4. Rules для Storage

```
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /chat_images/{chatId}/{fileName} {
      allow read: if request.auth != null;
      allow write: if request.auth != null
                   && request.resource.size < 5 * 1024 * 1024
                   && request.resource.contentType.matches('image/.*');
    }
  }
}
```

### 6.5. Порядок настройки (делает Р1)

1. `console.firebase.google.com` → **Add project** → имя, Analytics можно выключить.
2. **Add app → Android** → package `com.example.messenger` (ровно как `applicationId`).
3. Скачать `google-services.json` → положить в `app/`.
4. Плагин `com.google.gms.google-services` + Firebase BoM + `auth-ktx`, `database-ktx`, `storage-ktx`.
5. **Authentication → Sign-in method → Email/Password → Enable**.
6. **Realtime Database → Create database** → регион → вставить rules → включить `.indexOn`.
7. **Storage → Get started** → вставить rules.
8. Проверка: запустить приложение, создать пользователя, увидеть его во вкладке **Authentication → Users**.
9. Создать `demo1@example.com` и `demo2@example.com` (пароль `demo1234`), проверить вход обоими.
10. Перед защитой: rules не в тестовом режиме, экспорт JSON базы лежит в `docs/backup/`.

SHA-1 и Google Sign-In не нужны: вход только по email/паролю.

### 8.1. Git

- Ревью: Р1 обязательно; если PR трогает чужую папку — плюс владелец папки.
- Теги: `v0.1`…`v0.4` после занятий 1–4, `v1.0-rc` после занятия 5, `v1.0` перед защитой.

Задача готова к работе, если: есть контракт, понятно, какие файлы менять, есть тестовые данные и критерий приёмки. Если чего-то нет — задача не берётся, а формулируется вопрос.

- [ ] Сценарий работает на устройстве/эмуляторе.
- [ ] Нет крашей и `TODO` без issue.

### 8.5. Коммуникация

- Один общий чат команды + теги `@роль`.

- Спор о контракте решает Р1; спор о UI — Р3; спор о схеме — Р4 при согласии Р1.

2. Сообщить в чат «main красный, чиню».

### 9.5. Как объяснить «локальный сервис» (10 баллов)

Формулировка для защиты:

> «Локальный» здесь — не про телефон, а про контур организации. Мы разворачиваем собственный проект Firebase, доступ только через аккаунты команды, правила ограничивают чаты участниками, данные не уходят в публичные мессенджеры. Этого достаточно для небольшой распределённой команды: текст, фото, история. Полностью изолированный контур — следующий шаг: заменить Firebase на self-hosted сервер, архитектура репозиториев это позволит.

Не переусердствовать: если сказать «данные не покидают предприятие», комиссия справедливо спросит про Google-серверы. Честное ограничение сильнее громкого обещания.

Жизненный сценарий (Р5): бригада из 5 человек, смена, нужно скинуть фото повреждённого узла и договориться текстом; публичный мессенджер нельзя, история должна сохраняться.

## 10. Риски и запасные планы

| Риск | Вероятность | Что делаем |
|---|---|---|
| Р4 перегружен (самый большой участок) | высокая | Р1 подключается к Room/статусам после каркаса; урезаем счётчик непрочитанных до точки |
| Rules блокируют запись | средняя | тест двумя аккаунтами на занятии 2; временно открыть тестовый режим и закрыть до защиты |
| Эмулятор не стартует (нет виртуализации) | средняя | реальный телефон по USB; если нет — работать в паре с тем, у кого есть |
| Gradle/зависимости «поехали» | средняя | версии заморожены в неделю 0; никаких обновлений в процессе |
| Конфликты в общих файлах | высокая без правил | владение папками + один владелец у gradle/manifest/NavHost |
| Кто-то выпал из команды | средняя | медиа → Р3, доки/видео → Р1, auth → Р1; медиа урезаем до галереи без сжатия |
| API 23: краш из-за `java.time` | средняя | только `Long` + `SimpleDateFormat`; тест на API 23 раз в неделю |
| Медленная загрузка картинки | средняя | сжатие до 1280 px, прогресс, лимит 5 МБ, retry |
| `google-services.json` не тот package | низкая | Р1 проверяет `applicationId`; файл не перегенерировать без команды |
| Демо падает на защите | низкая | видео + APK + второй телефон + хотспот |

### 10.1. Что урезаем, если не успеваем (в порядке отказа)

1. Камера — оставляем только галерею (PDF допускает «или»).
2. Счётчик непрочитанных — оставляем точку.
3. Сжатие фото — грузим как есть, лимит 5 МБ.
4. Редактирование профиля — показываем email + выход.
5. Разделители дат — только время.
6. Тёмная тема.
7. Кэш списка чатов — офлайн показываем внутри диалога.

**Не режем никогда:** auth, список чатов, диалог, realtime-отправку, картинку, отметку прочтения, историю, APK, README, видео.

## 14. Главное

Проект разваливается не из-за сложности технологий, а из-за двух вещей: **общих файлов, которые правят все**, и **ожидания, пока другой сделает свою часть**. Здесь эти две проблемы закрыты: у каждого своя папка, а работа идёт против контрактов и заглушек. Если правило нарушается — это обсуждается на стендапе, а не молча чинится в чужом коде.
